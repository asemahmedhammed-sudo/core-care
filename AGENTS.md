# Core Care — Salla Theme Agent Guidelines

Core Care is a Salla Twilight storefront theme derived from the official Raed theme (Twig, JavaScript, SCSS, Tailwind CSS, Webpack). Implement changes inside this architecture and preserve Salla storefront behavior and merchant customization.

These instructions apply throughout the repository. Explicit user instructions take precedence over this file; more specific directory instructions apply within their scope. Do not treat old reports as proof of current preview access, deployed assets, or release readiness.

## 1. Non-negotiable rules

1. **Never edit `public/` by hand.** It is generated by Webpack. Edit sources and rebuild.
2. **Publishing, submitting for review, remote pushes, live-store changes, and destructive Git operations require user authorization.** Use authorization already provided for the action or requested workflow; do not ask again for the same scope.
3. **Never invent Salla capabilities.** Verify APIs, Twig variables, field types, hooks, and CLI options against official Salla docs or the installed package source.
4. **Never fabricate commerce values** (price, stock, rating, discount, currency). Use Salla data and supported components.
5. **Never leave unjustified whitespace** in a changed component or between it and its neighbors (see section 6).
6. **Never claim more than the evidence shows.** Distinguish "implemented", "repo checks passed", "Salla platform verified", and "release ready" whenever reporting those results.
7. **Never put secrets in the repo**: credentials, tokens, customer data, private preview URLs (also not in screenshots or logs).
8. **Preserve unrelated changes**, including existing generated assets and evidence files.

## 2. Quick commands

Use the Node engine range and pnpm version declared in `package.json` and the committed `pnpm-lock.yaml`.

| Purpose | Command |
|---|---|
| Install | `pnpm install --frozen-lockfile` (never regenerate the lockfile for unrelated work) |
| Production build | `pnpm build` |
| Tests + static audit | `pnpm test` (writes `docs/evidence/technical/static-audit.json`) |
| Asset size report | `pnpm size:theme` |
| Local asset watch | `pnpm watch` (development assets; does not by itself verify the Salla storefront) |
| Actual Salla preview | Use the official development preview workflow with an authorized theme and test store (section 5) |

Fallback if the pnpm launcher fails for an unrelated environment reason (report the limitation):

```sh
./node_modules/.bin/webpack --mode production
node --test scripts/*.test.mjs
node scripts/audit-theme.mjs
```

## 4. Working approach

1. **Inspect first**: read the affected implementation and run `git status` before editing.
2. **Plan for non-trivial tasks**: for coordinated changes across components, platform integrations, merchant configuration, or build behavior, give a short plan covering affected files, risks, and checks. Routine edits do not need a separate plan file or approval step.
3. **Make focused changes** that fix the cause. No unrelated refactors, broad reformatting, or speculative abstractions.
4. **Follow existing patterns**: naming, component structure, initialization. Prefer existing helpers and dependencies; add a dependency only when the task requires it.
5. **Continue through verification.** Resolve routine choices using project conventions. Ask concise questions only when missing information materially affects scope or correctness; continue independent work while awaiting an answer.
6. **Dirty working tree**: if there are pre-existing uncommitted changes, work around them and do not revert, stash, or reformat them.

### Verification by impact

| Change | Required verification |
|---|---|
| **Documentation only, with no storefront or build effect** | Accuracy, referenced paths/commands, and `git diff --check`; no build or preview required |
| **Any visual change, including copy, colors, tokens, or translations** | Production build + tests + actual Salla desktop/mobile review of the changed element and neighboring sections (section 9) |
| **Interactive or commerce behavior** | Production build + tests + focused regression coverage where applicable + affected interactions and states in the actual Salla preview |
| **Shared or structural change** | Production build + tests + review of affected routes and merchant compatibility; apply the visual/functional checks above when their behavior changes |

Choose verification according to observable impact, not line count. Small visual edits still require actual platform review; expand testing when a change introduces broader effects.

### Authorization and evidence handling

- Remote pushes, publication, review submission, live-store changes, and destructive Git operations need authorization covering that action or workflow. Read-only inspection and routine local edits/checks within the requested task do not need extra approval.
- Creating dated verification records and regenerating audit or size reports are part of authorized verification. Preserve unrelated evidence and historical results; do not delete them or rewrite past outcomes to conceal failures.
- When the task requires a dependency change, update its lockfile as part of that change. Do not regenerate the lockfile for unrelated work.

## 5. Salla integration and merchant configuration

### Platform behavior

- Preserve layout blocks, Salla hooks, asset loading order, and SDK/custom-element initialization order. Review shared changes for effects on other pages.
- Use supported Salla components (for example `salla-*` custom elements) for products, cart actions, wishlist, and customer state instead of replacing them with custom logic.
- Use the translation helper in Twig and the existing locale system; keep currency and number formatting platform-driven.

### Salla CLI

- Verify unfamiliar commands and flags using the installed CLI help or official documentation; do not assume options or publication command names.
- Read-only status checks and previewing an authorized development theme/test store are part of development verification and do not need repeated approval. Inspect preview side effects before running it; preview authorization does not authorize an unrelated commit or remote push.
- Publication, review submission, and changes to a live store require authorization covering that action.

### Editable components and `twilight.json`

- Keep the `twilight.json` definition, Twig field references, defaults, and conditional rendering consistent.
- Preserve existing setting IDs, field IDs, and component paths unless the task requires a migration. When renaming, removing, or changing a field type, state the compatibility consequence: merchants' saved values may be lost or ignored.
- Make intended merchant-controlled content editable. Handle empty, missing, disabled, and partially configured fields without broken links, broken markup, or reserved empty space.
- Support repeated component instances with scoped selectors and unique IDs. Avoid duplicate listeners, timers, or requests on re-initialization.
- Respect editor insertion markers, hidden components, and merchant-defined ordering. Never rely on a fixed homepage sequence.
- When merchant-facing behavior changes, update the relevant part of `docs/MERCHANT_GUIDE.md`.

## 6. Visual design and spacing (mandatory)

Applies to every page and element (sections, headings, cards, categories, banners, sliders) on desktop and mobile.

### Rules

- **Single owner of homepage spacing**: `#main-content` controls the gap between sections via `--beauty-section-gap` in `src/assets/styles/06-beauty/core-care-home.scss`. Do not add section margins that stack on top of the flex gap.
- **Section gap**: 24–40px depending on viewport width.
- **Visible content-to-content distance**: balanced, normally within 80px. More requires a documented design reason and visual review. These are Core Care design rules, not Salla acceptance thresholds.
- **Heading-to-content** spacing must be smaller than spacing between sections. Never use empty elements or fixed heights to adjust spacing.
- **Measure** from the end of visible content to the start of the next visible content, including internal padding and unused container height, not only between HTML boundaries.
- **Excess space** (for example below "Shop by category" and before the next banner) is a defect. Inspect `height`, `min-height`, `padding`, `margin`, `gap`, slider dimensions, hidden items, and editor wrappers, and fix the responsible component. Do not hide it with negative margins, clipping, or a global reset.
- **Adjacent sections** that are visually connected (for example the feature strip under the hero) stay adjacent when components are hidden or reordered, in both RTL and LTR.
- **Empty or hidden components release their space.** Low item counts and absent optional images must not reserve room. Images that do exist keep dimensions or aspect ratio to prevent layout shift.
- Use the Nice One visual reference below for the requested storefront appearance. Reuse the project's token structure and scope styles to avoid affecting unrelated shared Salla elements.
- For each UI change, inspect the changed section and its immediate previous and next sections: no abnormal gap, clipped content, overlapping cards, or unintended horizontal overflow.

### 6.1. Nice One visual reference: source and priority

**Reference:** [Nice One Arabic storefront](https://niceonesa.com/ar), inspected on **2026-10-04**. Match its visual system closely when implementing the requested Core Care storefront: neutral surfaces, compact Arabic typography, black actions, pink sale prices, outline icons, image-led campaigns, and a purple support footer.

Measured from the public storefront and CSS/SVG assets, not an official brand manual. Inspected: homepage, perfume collection, product detail, navigation, footer, empty cart, and English collection at desktop (1440px) and mobile (390px) widths. Chrome was unavailable; the Codex in-app browser was used. Desktop screenshots were constrained by the app surface; geometry also used rendered DOM measurements. This research does not verify Core Care on Salla.

- For this requested appearance, these values take precedence over legacy olive, cream, gold, or rose defaults in the beauty styles. Preserve existing setting IDs and merchant overrides when implementing the new default palette.
- Keep Core Care's configured logo, content, contacts, legal details, commerce data, and integrations. Do not copy Nice One business details or fabricate reference campaigns, coupons, ratings, or stock messages.
- The mandatory spacing rules above and accessibility rules below still apply. Reproduce the intended appearance while correcting observed overflow and unnecessary empty space.
- Values are sampled observations unless labeled **implementation target**; they are not universal fixed dimensions.
- Account/login, populated cart, checkout, and every campaign/state were not inspected. Apply shared tokens to theme-controlled surfaces; inspect unobserved states before claiming parity. Preserve platform-owned checkout.

### 6.6. Page and component composition

**Container/breakpoints.** Centered, full width constrained by viewport. Inspected max-widths: 640px from 640px, 768px from 768px, 1024px from 1024px, 1440px from 1280px. Use existing responsive utilities and contextual 12–24px inline gutters.

**Header/navigation.** Pink announcement strip: about 40px high, small centered white text, merchant-controlled. Desktop: white logo/search row about 75px high, then a 59px navigation/utility row with subtle bottom border and sticky positioning. Use broad pale-gray search and compact category/brand, account, language, bell, and bag actions. Start logo/navigation on the RTL right and reflow for LTR. Mobile hides the large logo/slogan and full navigation labels, retaining search (sample row 53px) and compact utilities/categories (59px). Preserve Salla customer, search, and cart components.

**Homepage.** Lead with a rounded promotional image carousel (sample art about 4:1 desktop/mobile), white circular arrows, and understated pagination. Follow with titled product carousels, wide campaigns, paired tiles, and product groups. Title at inline-start; small view-all link at inline-end. Preserve merchant ordering/optional sections. Avoid the legacy cream/olive split hero or oversized decorative whitespace.

**Product carousels/cards.** Sample slide widths: about 129px at 390px (16px gaps, next-card peek), 188px at 1440px. Match responsive density, not fixed universal widths. White cards contain centered media, optional status pill, circular quick-add/options, rating/reviews, brand, compact name, and prices. Sale/discount is pink; regular price dark. Preserve existing-image geometry during loading; absent metadata releases space. Keep supported option selection. Never fake reviews, timers, or badges.

**Collection/search.** Compact title/sort row and optional category pills about 8px apart. Grid: **2 columns below 768px, 3 from 768px, 4 from 1024px, 6 from 1280px**, with 12px gaps. Desktop filter sidebar is separated by 20px and sits on the RTL right; mobile hides the full sidebar. Keep compact groups/checkboxes and existing mobile filtering; the opened mobile panel was not measured. Prevent horizontal page overflow.

**Product detail.** White desktop columns: gallery on RTL right, purchase information left, approximately 24px padding/gap. Contained main image and vertical thumbnail rail; mobile stacks gallery/information and the inspected rail remains vertical. Include Salla-provided brand/title, ratings, price/tax, supported installments, black purchase CTA, detail/specification accordions, seller, recommendations, reviews. Titles wrap naturally. Observed floating white purchase bar: thumbnail, name/price, CTA; about 75% available width mobile/40% larger screens, bottom 32px. Preserve action state, safe areas, and unobstructed content/overlays.

**Cart drawer.** Empty cart: white viewport-height drawer from the left, 70% black backdrop, compact header actions, about 80px bag illustration/pale purple circle, dark heading, muted copy, black shopping CTA, recommendations. Desktop width: 500px. **Implementation target:** `width: min(500px, 100vw)` and internal scrolling, correcting observed mobile overflow. Preserve focus/close behavior and Salla state. Filled-cart geometry was not inspected.

**Footer.** Purple support band: white heading, soft light copy, line contact/help icons. Very light lower footer: configured navigation, social/app links, payments, copyright, merchant legal details. Reflow on narrow screens; absent content leaves no placeholders. Do not copy reference contacts/registrations/app links. Detailed mobile transitions and every link group were not measured.

### 6.7. Implementation mapping and visual acceptance

- Apply shared tokens/font defaults in `src/assets/styles/06-beauty/beauty.scss`; adapt header, products, categories, campaigns, product details, and footer in their existing `core-care-*.scss` files. Keep `core-care-home.scss` as the owner of section rhythm. Inspect the relevant Twig/JS/Salla component before styling its states.
- Implement with Twig/SCSS/JavaScript and Salla; do not introduce Nuxt, Vue, Vant, or duplicate commerce logic to match reference frameworks.
- Keep hover/focus/pressed/disabled/loading/empty/error/selected/unavailable states usable. Only menu hover/active chips were measured; inspect other state colors/motion for exact matching. Respect reduced motion.
- Compare equivalent elements at the same viewport: fonts/wrapping, colors, icon silhouettes, density, image fit, corners, header heights, footer. Record differences for merchant data/controls, accessibility, or overflow fixes.
- Verify both RTL/LTR and desktop/mobile through section 9. An updated guideline, a copied palette, or a local screenshot alone does not establish visual parity. Mark uninspected reference states and incomplete Salla checks explicitly.

## 7. Localization, accessibility, performance

- Add storefront strings through the translation system; keep `ar.json` and `en.json` keys aligned. Include accessible labels and empty/error states.
- Support Arabic RTL and English LTR. Prefer logical CSS properties; check directional icons, slider controls, and mixed currency/number text.
- Use semantic headings, links for navigation, buttons for actions. Provide accessible names, visible keyboard focus, appropriate image alt text, and correct state attributes (`aria-expanded`, `aria-selected`, and so on).
- Preserve keyboard operation and focus behavior. Respect `prefers-reduced-motion`. Never make essential information hover-only.
- Keep layouts usable at narrow widths, with long text, and with absent optional content. Do not use overflow clipping to hide layout defects.
- Reserve image dimensions, size images suitably, lazy-load below-the-fold media, and do not delay critical visible content.
- Reuse platform feeds and batch data loading. Avoid per-card product requests or repeated loading of the same data.

## 8. Template and frontend security

- Escape text, attributes, and URLs for their output context. Validate configurable URL schemes before using them for links or media.
- Do not introduce `|raw` in new custom templates. Review modified inherited `|raw` expressions for their trust boundary; upstream origin does not prove safety.
- Use `textContent` for plain text. Validate attribute names and values for their context; `setAttribute` alone does not make a URL or event-handler attribute safe. Do not insert merchant or product values with `innerHTML` without context-appropriate sanitization and escaping.
- Preserve existing security checks in product cards, menus, banners, and navigation helpers.

## 9. Build and verification

### Repository checks

For changes to UI, JavaScript, SCSS, Twig, locales, theme configuration, or build behavior, run `pnpm build` and `pnpm test`.

- Add or update focused regression tests for behavior changes and reproducible defects. Test observable behavior and meaningful edge cases, not implementation details.
- After SCSS or Twig changes, inspect the relevant generated `public/` assets, template asset references, and the build diff. A successful Webpack build does not prove Twig renders correctly on Salla.
- Inspect the change to `docs/evidence/technical/static-audit.json` and preserve any pre-existing work in it.
- Run `pnpm size:theme` when asset weight or loading changes materially. Size reports are measurements, not platform acceptance.
- If preview/watch tooling overwrote `public/` with development output, restore it with a final production build before handoff.
- Fix failures you introduced. Report unrelated failures and material warnings without altering the baseline or claiming a clean result.

### Actual Salla visual and functional verification (every UI or visual change)

1. Load the updated version through the real Salla preview workflow and confirm the preview serves the changed assets. A refresh or successful build alone is insufficient when draft assets are cached.
2. In Chrome, inspect the changed section and its immediate neighbors at desktop and mobile widths (for example 1440px and 390px; add 320px and affected breakpoints for responsive changes).
3. Record heading-to-content and content-to-content gaps for desktop and mobile. Review normal content, low item counts, missing optional images/text, hidden components, and editor reordering for the changed component. Check RTL and LTR when direction can affect the change. The sample viewports are project verification choices, not Salla acceptance thresholds.
4. Exercise affected interactions and states. For commerce changes include price/options, unavailable products, quantity, cart, and wishlist using authorized test data.
5. Save a dated record under `docs/tests/` with: source revision or working-tree state, preview/build identity, browser, viewport, steps, actual result, evidence paths, untested cases. Redact secrets.

Environment honesty: a static local preview does not prove Salla runtime behavior. A live development preview with locally served assets validates that configuration only; it does not prove the hosted draft has the same build. State which environment was verified.

If Chrome, authentication, deployment, or editor access is unavailable, complete independent checks, record the exact limitation, and mark platform visual verification as **incomplete**. An alternate browser gives partial evidence only; do not claim Chrome verification.

## 10. Completion and handoff

Do not mark a UI change complete while unjustified whitespace remains in the changed component or between its neighbors.

Final report (in the user's language unless requested otherwise) must include:

- What changed and why.
- Checks run and their actual results (including failures and warnings).
- Generated assets and merchant configuration changes, if any.
- Compatibility consequences (setting IDs, field types, migrations), if any.
- Distinguish **implementation complete**, **repository checks passed**, **platform verification completed**, and **publication readiness** when relevant. Use passed, failed, incomplete, or not applicable accurately; documentation-only tasks do not need a release-status checklist. Never claim Salla approval or release readiness without matching evidence.
- Remaining limitations and untested cases.
